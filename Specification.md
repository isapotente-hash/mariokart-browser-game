Mario Kart 8 Deluxe Browser Game Development Prompt
GitHub repository and GitHub Pages release
01 Project objective and delivery contract
Act as a senior browser game developer, gameplay programmer, technical artist, and release engineer. Build a playable 3D kart racing game in a GitHub repository, using Mario Kart 8 Deluxe as the gameplay reference. Deliver source code, working game content, tests, and a GitHub Pages deployment workflow. The result must be a game that visitors can open and play from a URL.
The experience to create
Capture responsive arcade handling, readable racing lines, satisfying drifts, tactical items, lively opponents, colourful courses, and dramatic finishes. Prioritise the feel of driving over the quantity of content. Use the Deluxe reference for two item slots, dedicated battle arenas, driving assists, and varied traversal. Treat every numerical value in this prompt as a tunable project requirement rather than a claim about Nintendo source code.
Platform and public build
Use TypeScript, Three.js, Vite, HTML, and CSS. Run the game entirely in the browser, with compiled static files hosted on GitHub Pages. Bundle dependencies through the build. Use original procedural visuals and audio, appropriately licensed assets, or assets explicitly supplied for this project. Make the public game title configurable. Keep character, track, item, and sound definitions replaceable without rewriting the game systems.
Use desktop keyboard controls first, gamepad support second, and landscape touch controls third. Target recent stable desktop Chrome, Edge, Firefox, and Safari where the required graphics features are available. Include capability detection and a useful unsupported-device screen. Online matchmaking is outside the static release; single player, AI opponents, local saves, and local multiplayer provide the playable experience.
Required release and expanded scope
First complete a vertical slice with one course, one player, seven AI racers, drifting, three items, lap counting, results, and deployment. Then complete the release target: four courses, twelve total racers per race, eight selectable drivers, vehicle customisation, eight items, Grand Prix, Versus, Time Trial, and two-player split screen. Include an anti-gravity section, underwater section, and gliding section across the four courses.
How to execute this prompt
Read all ten pages as one specification. Inspect the repository before editing; preserve useful existing work. Make reasonable implementation decisions and record them briefly. Implement working files rather than returning only a plan. Finish each milestone in a runnable state, verify it, and continue. Report a feature as complete only when it works in the built browser game. Expanded battle content follows the release target on page nine.

 02 Repository and browser architecture
Create a small, understandable codebase with a clear boundary between the simulation, rendering, interface, content data, and browser platform services. Avoid a single oversized game file. Prefer simple modules and explicit ownership over a complex framework. The repository must remain easy to clone, install, run, test, and publish.
Project structure
•	Place the entry page at index.html and application entry code in src/main.ts. Put core lifecycle and timing in src/core, vehicle systems in src/gameplay, opponent logic in src/ai, course definitions in src/tracks, and item behaviour in src/items.
•	Use src/rendering for cameras, lighting, scene construction, and effects; src/ui for menus and HUD; src/platform for input, audio, saves, and capability detection; src/data for typed content definitions; and tests for meaningful automated checks.
•	Keep imported media under public/assets or import build-managed assets from source modules. Include package.json, a committed lockfile, TypeScript and Vite configuration, .gitignore, README.md, and .github/workflows/deploy.yml. Do not commit node_modules, credentials, or generated caches.
Simulation contract
Advance gameplay with a fixed 60 Hz simulation step using an accumulator. Render with requestAnimationFrame and interpolate visual transforms when useful. Clamp accumulated time after stalls, limit catch-up steps, and pause appropriately when the tab loses visibility. Vehicle speed, drift charge, item timers, and race clocks must use simulation time rather than rendered frame counts.
Represent the race with explicit states: boot, loading, menu, countdown, racing, paused, finished, and results. State transitions own their input rules and cleanup. Give every racer a stable ID. Separate physical position from validated course progress. Use shared event types for pickups, hits, boosts, checkpoints, finish events, and interface updates so replay and debugging tools can observe the same events.
Static hosting boundaries
Use in-memory navigation or URL hashes for menu screens, avoiding server-dependent route rewrites. Resolve static assets through the configured application base. Do not rely on a Node server, filesystem writes, serverless functions, a database, or private environment variables at runtime. A normal static preview server must reproduce the production experience.
Use a seeded random generator for AI choices, item draws, and repeatable test scenarios. Deterministic test inputs should reproduce a simulation within documented numerical tolerances; do not promise identical cross-browser floating-point replays. Centralise tunable constants in typed configuration. Provide a development overlay for frame time, racer speed, current surface, drift state, checkpoint index, and item state, disabled in the public build by default.

 03 Driving physics and player controls
Create forgiving arcade kart handling that responds immediately while preserving momentum and a clear difference between gripping and drifting. Use a lightweight custom controller with surface sampling and simple collision shapes. Full vehicle suspension simulation is unnecessary. Keep the physical controller stable before adding body lean, wheel animations, particles, or camera shake.
Input and movement
Map W or Up to acceleration, S or Down to brake and reverse, A and D or Left and Right to steering, Space to hop and drift, E to use an item, Q to look behind, and Escape to pause. Allow remapping. Use braking before reverse, with a short stopped threshold to prevent accidental reversing. Provide a separate rearward item modifier, such as holding Down while pressing E, and explain it in the controls screen.
Apply speed-dependent steering, acceleration curves, rolling drag, maximum forward speed, reverse speed, lateral grip, and off-road resistance. Start with a medium kart reaching normal maximum speed in about three seconds. Keep all dimensions and speeds consistent in world units. Tune course scale and camera movement to create speed rather than relying on extreme velocity values.
Drifting and boosts
Enter a drift when the player hops while steering above a minimum speed. Lock the drift side until release while allowing controlled adjustment of the racing line. Charge a mini-turbo only during a sustained valid drift. Show blue, orange, and purple charge stages with distinct shapes or indicators as well as colour. Begin with thresholds around 0.7, 1.5, and 2.5 seconds, then tune through playtesting.
Release the drift button to trigger the earned boost. Cancel drift charge on major impacts, reset, or invalid movement. Define boost duration, acceleration, speed cap, and stacking rules in configuration. Reward a trick input inside a short ramp take-off window with a landing boost. Add an optional timed start boost with clear feedback; holding acceleration too early should produce a short stumble rather than an unexplained launch failure.
Collisions and recovery
Use swept or substepped collision checks where thin barriers and fast projectiles could be missed. Wall contact should slide and slow the kart without trapping or launching it. Resolve kart contact with bounded impulses. Cap speed and reject non-finite transforms. Use checkpoint rescue after falling or pressing a reset command: return to a safe forward-facing pose, apply a time penalty, and briefly prevent repeated damage.
Support optional auto-acceleration and steering assistance. The assist should gently guide a kart away from course edges and should never teleport it, choose shortcuts, or award progress. Make assistance settings visible before a race and persist them. Verify the same acceleration and drift timing at 30, 60, and 120 rendered frames per second.

 04 Course design and traversal systems
Build courses as real navigable 3D environments with a clear drivable ribbon, readable edges, ordered checkpoints, route samples for AI, recovery positions, and a simplified collision representation. Give every course a unique silhouette and landmark. Use original layouts with the playful variety associated with the reference game, rather than depending on imported commercial course geometry.
Four course release plan
•	Garden Circuit is the teaching course: wide turns, a gentle hill, one ramp, one optional off-road shortcut, and three clearly signposted laps. Use grass, painted kerbs, simple grandstands, and distant landmarks to establish a friendly opening race.
•	Harbour Run adds an underwater tunnel, docks, moving obstacles with visible cycles, and an alternate route. Keep the water entry and exit smooth; show bubbles and altered sound without hiding the next turn.
•	Sky Foundry introduces a banked anti-gravity wall, a glider launch, and a broad landing zone. Build a recovery route for missed landings. Preview gravity changes with track markings and wheel effects before the transition.
•	Starlight Causeway is the advanced course: tighter corners, exposed edges, chained drift opportunities, and a risky boost shortcut. Prioritise readable road contrast and stable camera orientation over dense visual effects.
Course data and progress
Store centreline samples, widths, surface normals, branches, checkpoint gates, spawn grids, item boxes, coins, hazards, and rescue poses in typed data. Rank racers using validated laps, checkpoint order, and continuous progress along the current route. A crossing must occur in the intended direction. Prevent repeated finish-line crossings, backwards laps, reset exploits, and shortcuts that skip mandatory checkpoints. Allow legitimate alternate routes to merge cleanly.
Special traversal
For anti-gravity, maintain a local track frame and smoothly align gravity and kart orientation to the sampled surface normal. Blend the chase camera and avoid abrupt world-up flips. Define controlled contact boosts for designated anti-gravity interactions. For underwater driving, tune drag and grip while preserving steering responsiveness. For gliding, use a distinct state with pitch, gentle yaw, bounded lift, descent, and a reliable return to grounded driving.
Make each transition explicit in course volumes and robust if entered at an unusual angle. A glider must not open on ordinary jumps. Surface effects must match actual handling. Keep hazards predictable, leave recovery space after difficult features, and place item boxes where players can see their choices. Validate every spawn and rescue pose against collision and checkpoint progression. Target roughly two to four minutes per race at the default speed class; adjust course scale after measuring actual lap times.

 05 Items coins and race balance
Implement items as gameplay systems with visible activation, consistent targeting, collision, damage responses, audio cues, and cleanup. Item icons alone do not count as implementation. Start with a banana-style trap, a bouncing shell projectile, and a mushroom-style boost. Expand only after those three work reliably with human and AI racers.
Two slot inventory
Use an active slot and a reserve slot. Draw only when inventory capacity is available; a double pickup may fill both empty slots. After consuming the active item, promote the reserve item automatically. Do not allow free slot swapping. Show a brief draw animation while preserving the underlying result. Use cooldowns and stable pickup IDs to prevent duplicate awards when a racer overlaps a box for several simulation steps.
Eight item release set
•	Trap: drop a visible obstacle ahead or behind with a short arming delay. Bouncing projectile: launch along the course, reflect from valid barriers, and expire after a bounded life or hit count.
•	Homing projectile: follow course-aware guidance toward the next eligible opponent, with warning and a turn-rate limit. Speed boost: increase speed briefly and reduce off-road penalty for the boost interval.
•	Timed explosive: travel briefly, display an arming cue, then apply an area hit. Shield burst: clear nearby threats and provide a short defensive window with an obvious radius effect.
•	Invincibility: grant temporary hit immunity and a moderate speed benefit, with a visible end cue. Leader strike: travel along the route toward the leading eligible racer, provide an advance warning, and allow the shield burst to counter it.
Distribution and damage rules
Use a configurable weighted table based on race position and distance behind the leader. Favour defence near the front and recovery tools farther back. Make high-impact items rare and restrict them during the opening seconds. Avoid giving a racer an item that has no valid use. Provide a developer command to force each item for testing. Keep game balance data separate from item implementation.
A hit applies a bounded spin, slowdown, and optional coin loss, followed by brief damage immunity. Define interaction priority so invincibility defeats ordinary hits, shields intercept eligible attacks, and one explosion cannot repeatedly damage the same racer. Pool transient objects and clear them on restart. Prevent self-hits during a short launch grace period, then apply the documented ownership rules.
Coins and fairness
Cap carried coins at ten and use a modest configurable speed benefit. Track race coins separately from long-term unlock currency. Place pickups along helpful racing lines and some risky alternatives. Record item frequency, hit chains, and race gaps during testing. Tune for comeback opportunities while keeping cornering and item timing valuable. AI uses the same pickup, inventory, cooldown, and damage rules as the player.

 06 Opponents race rules and game modes
Make AI opponents competent and readable. They should drive the course, recover from mistakes, drift where appropriate, and use items through the same gameplay interfaces as human players. Populate the vertical slice with seven AI racers and expand the release race to eleven AI racers when one human is playing. Two-player races should retain twelve total competitors.
AI driving and difficulty
Follow a sampled racing line with speed-dependent look-ahead. Calculate target speed from upcoming curvature, surface type, hazards, and braking distance. Allow lane offsets for overtaking and avoidance, with cooldowns to prevent oscillation. Use explicit normal, overtaking, recovering, and airborne behaviours. Detect a stuck kart from low progress over several seconds and recover it at a validated rescue point.
Give drivers seeded traits for aggression, line accuracy, reaction delay, drift confidence, and item timing. Easy opponents brake earlier and make more small errors; hard opponents drive cleaner lines. Any catch-up assistance must be bounded, documented, and disabled in competitive Time Trial comparisons. Do not teleport opponents or let them ignore collisions, cooldowns, or checkpoint validation.
Race rules and scoring
Create a visible starting grid, countdown, race clock, ordered lap events, wrong-way indicator, and stable finish order. Default to three laps but permit per-course configuration. When the player finishes, display results after opponents finish or after a timeout. Record actual finishers first and order remaining racers by validated progress with a clear unfinished status. Lock an accepted finish result against later simulation changes.
Grand Prix consists of the four release courses. Award configurable points of 15, 12, 10, 9, 8, 7, 6, 5, 4, 3, 2, and 1 for places one through twelve. Resolve cup ties by race wins, then best final-race position. Show points after every race and a final podium. This scoring table is the project default and should be data-driven.
Required playable modes
•	Versus lets the player select course, AI difficulty, speed class, lap count, and item settings. Provide 50cc, 100cc, 150cc, and 200cc presets as tuned speed profiles, plus a mirrored-course option where geometry and navigation are actually mirrored.
•	Time Trial disables opponents and random item draws, uses a fixed three-boost inventory per run, saves personal bests, and optionally displays a local ghost. Store sampled transforms for the ghost with track and physics version identifiers.
•	Grand Prix persists the current cup between races and offers restart or abandon choices. Each mode must have a complete path from menu to race to results and back, with no dead buttons or inaccessible screens.

 07 Visuals audio interface and accessibility
Give the game a cohesive, bright 3D appearance that remains readable at racing speed. Use stylised procedural models, strong material colours, soft lighting, and restrained effects. Make polished low-complexity art the baseline so the repository builds without a large external asset download. The driving surface and next turn should remain clearer than the scenery.
Drivers vehicles and camera
Provide eight selectable original drivers covering light, medium, and heavy handling profiles. Include at least three chassis, three tyre sets, and two gliders, with visible changes and small stat tradeoffs. Show speed, acceleration, handling, grip, and drift potential in the selection screen. Calculate final stats from one documented formula and validate combinations so no build becomes unusable.
Animate wheel rotation, steering, body lean, hop, drift, damage, and finish celebration. Use a spring-smoothed chase camera with collision avoidance, a speed-sensitive field of view, and restrained boost feedback. Rear view must work while held. Provide reduced camera shake and reduced motion settings. Keep the kart, landing zone, and upcoming turn visible during gliding and anti-gravity transitions.
Menus and race information
Build title, mode selection, driver and vehicle selection, course selection, settings, loading, pause, and results screens. The HUD shows position, lap, coins, two item slots, race time, mini-map, and urgent attack warnings. Support both human viewports in split screen. Use DOM interfaces for sharp text and accessible controls, with a clear focus indicator and keyboard navigation. Explain controls before the first race and make them available from pause.
Show meaningful loading progress for known assets and provide retry or return options after a load failure. Restart must reliably dispose of the previous race. Pause must freeze single-player gameplay and sound appropriately. Fullscreen is optional and must be requested through a user action. Resize the canvas and HUD correctly without resetting the race.
Audio and inclusive controls
Unlock browser audio after an explicit user gesture. Provide master, music, and effects volumes and persist them. Include engine pitch changes, drift charge cues, item warnings, pickup sounds, impacts, countdown, and finish feedback. Use original short music loops or clearly credited reusable music. Cap simultaneous sound effects and prioritise important warnings. Muting must silence all channels.
Pair audio warnings with visible cues. Never communicate drift charge, team identity, or danger only through colour. Keep text legible against varied scenery, provide scalable HUD sizing, and avoid flashing effects. Touch controls need large targets, multi-touch support, and protection against page scrolling during play. Keep normal browser navigation available in menus. Persist control mapping, assists, volume, and quality independently from race progress.

 08 Browser performance local multiplayer and saves
Optimise for an enjoyable browser session on ordinary hardware. Set an initial target of 60 frames per second at 1080p on a representative midrange desktop and a stable 30 frames per second on a representative mobile device using low settings. These are acceptance targets to measure and report, not guaranteed claims. Record the tested hardware, browser, scene, and quality level.
Rendering and asset budgets
Use instancing for repeated scenery, simplified collision geometry, object pools for projectiles and particles, and limited dynamic shadows. Cache track queries and reuse temporary vectors in tight loops. Add low, medium, and high quality presets controlling pixel ratio, shadows, particles, draw distance, and decoration density. Keep racing rules and visibility of important hazards consistent across presets.
Cap device pixel ratio by quality level and resize render targets only when needed. Load only the selected course and shared content before a race; defer other tracks. Aim for an initial compressed transfer below 15 MB and document measured size. Show progress during loading. Use compressed textures and models when imported content justifies them, while keeping procedural fallback assets available.
Two player split screen
Run one shared simulation with two cameras and two independent HUDs. Offer side-by-side or stacked viewports based on screen shape. Support two gamepads, or keyboard plus gamepad; two players on one keyboard may be optional because of key rollover. Give each human a distinct input assignment. Never let one player navigation event activate another player menu.
Apply difficulty and item rules consistently to both players. Pause the shared local race through a clear common pause screen. Handle controller disconnects with a prompt to reconnect or reassign. Reduce expensive per-camera effects when split screen is active. Test player-specific rear view, wrong-way warnings, item icons, finish state, and camera bounds. Touch split screen is outside the release target.
Local data and browser resilience
Store settings, unlocks, and cup progress in a small versioned localStorage record. Use IndexedDB for larger ghost recordings if implemented. Validate loaded values, migrate known schema versions, and handle storage denial or corruption gracefully. Offer reset progress with confirmation and optional JSON export and import. Label records as local to the browser and device; do not show a fictional global leaderboard.
Handle visibility changes, window resize, lost input focus, graphics context loss, and unavailable audio without an unexplained blank screen. Release geometry, materials, textures, render targets, event listeners, and audio nodes on teardown. Check repeated race restarts for accumulating objects or memory. Avoid requiring SharedArrayBuffer, cross-origin isolation headers, or special server configuration for the default Pages build.

 09 Milestones expanded content and verification
Work in milestones with demonstrable exit conditions. Keep the default branch buildable. If the environment limits what can be executed, finish the files you can, state the exact unverified checks, and avoid claiming a successful browser run. A milestone is complete when its behaviour has been exercised, not when a file with the expected name exists.
Implementation sequence
•	Milestone one establishes the repository, static build, Pages workflow, title screen, procedural test course, kart controller, chase camera, and restart. Exit when the built game loads under a repository subpath and a player can drive a full valid lap.
•	Milestone two completes the vertical slice: seven AI opponents, countdown, three laps, three functioning items, drift boosts, rescue, HUD, and results. Exit after a complete race and restart with no blocking errors.
•	Milestone three completes the release scope: four courses, twelve racers, eight drivers, customisation, all eight items, traversal systems, required modes, split screen, saves, audio, and quality presets. Exit when each feature is accessible and usable in the production build.
•	Milestone four adds battle content after the release checks pass. Build a compact arena with item routes, multiple approach paths, safe spawns, and AI navigation. Implement Balloon Battle first, with a visible timer, score for successful hits, respawn rules, and an unambiguous winner.
Further Deluxe reference modes
For expanded battle coverage, add an explosive-only battle, coin collection contest, a timed possession contest, and a team capture-and-rescue mode. Keep each rule set in separate data and logic. These correspond to the reference ideas behind Bob-omb Blast, Coin Runners, Shine Thief, and Renegade Roundup; use original presentation. Show expanded modes only when implemented. Keep online play as a separately scoped future project requiring additional infrastructure.
Automated and manual checks
Write meaningful tests for checkpoint order, finish locking, race ranking, cup scoring, inventory promotion, item hit immunity, weighted item eligibility, and save validation. Use a browser smoke test to load the built app, start a seeded race, exercise controls, and verify a nonblank rendered scene without console errors. Include a shortened deterministic test course so completion checks are practical.
Manually test drift stages, all eight items, backwards driving, shortcut rejection, reset near the finish, simultaneous hits, wall sliding, water entry, glider landing, anti-gravity transitions, controller disconnect, pause, muted audio, denied storage, touch controls, and resize. Compare driving across frame rates. Check cold load, refresh, and asset requests under the actual deployment base. Fix failures before expanding content; list any remaining limitations precisely.

 10 GitHub Pages publishing and final handover
Finish with a repository that another person can publish without repairing paths or inventing missing files. Use GitHub Actions to build and deploy the static production output. GitHub Pages serves static HTML, CSS, JavaScript, and assets; all race simulation therefore stays in the browser. An automated build must reproduce the same playable game as the local production preview.
Build and deployment requirements
Provide working npm scripts for dev, build, preview, typecheck, and test. Choose a supported Node release compatible with the selected toolchain and use it consistently in documentation and Actions. Commit the dependency lockfile and install with npm ci in continuous integration. Run type checking, automated tests, and the production build before uploading the deployment artifact.
Configure Vite for both an account site and a repository project site. Use base / for an account site or custom domain, and /REPOSITORY_NAME/ for a project site. Make the value configurable and show the exact place to change it. Resolve runtime media with import.meta.env.BASE_URL or build-managed imports so models, textures, sound, and icons load below the repository path. Do not hardcode a leading slash for project assets.
Create a deploy workflow triggered by pushes to the default branch and by manual dispatch. Use currently supported official checkout, Node setup, Pages configuration, artifact upload, and deployment actions. Grant contents read, pages write, and id-token write only where needed. Use the github-pages environment and expose the deployment URL from the deployment step. Upload dist as the Pages artifact. Keep pull-request validation separate from production deployment.
Publishing instructions for the owner
Explain how to create or choose a GitHub repository, push the project, set the correct base path, select GitHub Actions in Settings then Pages, run the workflow, and find the published URL. Explain how later pushes update the site. If repository access is available and publishing is authorised, perform those steps; otherwise deliver the complete ready-to-push project and identify the remaining owner action. Never invent a deployed URL.
Definition of done
The README must include controls, prerequisites, local run commands, production preview, deployment steps, feature status, measured performance, asset credits, and troubleshooting for blank screens, missing assets, muted audio, and stale browser data. Include screenshots from an actual run when capture is available. Summarise completed milestones, checks that passed, checks not run, and any known issues. Provide repository and live links only when verified.
Begin implementing now. Deliver a complete vertical slice before expanding the game, continue through the release milestones, and preserve an honest feature status throughout. The final result must be playable from its GitHub Pages URL with no installation for visitors.
